# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this
repository's `frontend/`.

## Project state

TanStack Start app (React) that consumes `../backend`'s FastAPI service. Scaffolded with the
official `tanstack create` CLI (framework react, package manager bun, toolchain biome, deployment
adapter nitro, no demo pages), then built out into a real app: three routes covering the reports
list, a report's rows, and the extraction run status. No auth here either -- matches the backend's
current state (see `backend/CLAUDE.md`'s security note); this frontend has no login of its own.

## Tooling

Managed by **bun** (`bun.lock`). Biome for lint/format (`biome.json`); no ESLint/Prettier.

```bash
bun install
bun run dev          # vite dev, port 3000
bun run typecheck    # tsc --noEmit (no dedicated test suite yet)
bun run check        # biome check (lint + format)
bun run build         # client + SSR + Nitro server bundle -> .output/
bun run start         # bun run .output/server/index.mjs
```

## Setup

Copy `.env.example` to `.env` and set `C3_API_URL` (defaults to `http://127.0.0.1:8000`, the
backend's default `uvicorn` port). Read only in `src/server/backend.server.ts` (server-only, see
below) -- never exposed to the client bundle.

```
  routes/

                             backfill/contacts-sync/historical-backfill cards
  components/
    ui/                      shadcn-generated, vendored -- see "UI (shadcn)" below
    theme-provider.tsx        light/dark/system, copied from ../../RCTM_WEB's pattern
    toaster.tsx                sonner wrapper wired to the theme
    site-header.tsx             nav (Reportes/Extraction status) + ModeToggle, in every page via __root.tsx
    mode-toggle.tsx               DropdownMenu-based theme switcher
    auto-refresh-provider.tsx      the client-side "cron" that replaced the backend's scheduler --
                                   see "Client-side auto-refresh" below
    status-donut-chart.tsx          MUI X Charts donut -- see "Charts (MUI X Charts)" below
    agent-workload-chart.tsx        MUI X Charts horizontal bar -- see "Charts (MUI X Charts)" below
    mui-chart-theme.tsx              ChartThemeProvider -- syncs an MUI theme to this app's dark/light
                                     class so chart chrome isn't stuck on MUI's unthemed light defaults
  lib/
    utils.ts                cn() -- clsx + tailwind-merge, shadcn's standard helper
    auto-refresh-settings.ts  pure logic (no React) behind auto-refresh-provider.tsx: types,
                              localStorage read/write, interval-to-ms conversion
  server/
    schemas.ts              client-safe: REPORT_NAMES/ReportName, zod schemas, response types
    backend.server.ts        server-only: fetch() calls to the FastAPI backend, reads C3_API_URL
    reports.functions.ts      createServerFn wrappers around backend.server.ts -- safe to import
                              anywhere (routes, components, other server functions)
```

**Server-only boundary convention** (from TanStack Start's own docs, see
"Server Functions" -> "File Organization"): `*.server.ts` is never imported outside a
`createServerFn().handler()`; `*.functions.ts` exports the `createServerFn` wrappers and is safe to
import from client code (the build strips the handler bodies out of the client bundle and replaces
calls with RPC stubs); plain `.ts` (here, `schemas.ts`) is client-safe shared shapes/constants. This
is why `C3_API_URL` is read in `backend.server.ts` and nowhere else -- it would otherwise leak into
the client bundle.

`REPORT_NAMES` in `schemas.ts` is kept in sync **by hand** with
`backend/app/routers/data.py`'s `_KNOWN_REPORTS` -- there's no shared import across the Python/TS
boundary, so if a report name is ever added on the backend, add it here too.

## UI (shadcn)

Installed with the official `shadcn` CLI, matching `../../RCTM_WEB`'s setup exactly so Casa Market's
tools stay visually/structurally consistent, with only the color hue changed:

```bash
bunx shadcn@latest init --template start --base base --preset maia
```

- **`--base base`**: components are built on **Base UI** (`@base-ui/react`) primitives, not Radix.
  This matters for composition -- Base UI uses a `render={<Button .../>}` prop instead of Radix's
  `asChild` (see `components/mode-toggle.tsx`'s `DropdownMenuTrigger` for an example, or
  `components/ui/sheet.tsx`'s close button).
- **`--preset maia`**: `components.json`'s `"style": "base-maia"` -- a specific shadcn registry
  preset (pill-shaped buttons/`rounded-4xl`, `oklch()` color tokens, a defined shadow/radius scale).
  Not something to regenerate casually; if it ever needs re-running, note the CLI's `init` writes to
  wherever `components.json.tailwind.css` points, which had to be hand-corrected to `src/styles.css`
  after the first run (it defaulted to a Next.js-shaped `app/globals.css` that doesn't exist here).
- **Icon library**: `lucide-react` (matches RCTM_WEB; the CLI's own default is `hugeicons`, fixed by
  hand in `components.json`).
- **Aliases**: `#/components`, `#/lib/utils`, etc. -- matches this project's own `#/*` subpath import
  convention (`package.json`'s `imports` field), not the CLI's default `@/*`.

**Theme**: same OKLCH recipe as `../../RCTM_WEB/src/styles.css` (identical lightness/chroma per
token/mode), with the hue rotated from 45 (orange) to ~16 (red/rose) everywhere it appears as the
brand color (`--primary`, `--ring`, `--chart-1`, `--sidebar-primary`, the light-mode `--accent`/
`--sidebar-accent` tints). The hue comes from converting `/home/ivan/lab/apps/iv4n.dev`'s actual
accent hex (`#f43f5e` light / `#fb7185` dark) to OKLCH -- not picked by eye -- so it's the same red
family as that reference, not an approximation. Font is Figtree (the preset's default; RCTM_WEB also
layers in Geist, which wasn't pulled in here and wasn't added speculatively).

**Dark mode**: `components/theme-provider.tsx` is copied verbatim from
`../../RCTM_WEB/src/components/context/theme-provider.tsx` (a plain React Context + `localStorage`,
no `next-themes` despite it being a transitive dependency of `sonner`/the preset -- don't switch to
it, this custom provider is the established pattern here and in RCTM_WEB). Toggled via
`components/mode-toggle.tsx` (classic shadcn light/dark/system `DropdownMenu`), reachable from
`components/site-header.tsx` on every page. `<html suppressHydrationWarning>` in `__root.tsx` is
required -- the provider sets the `dark`/`light` class client-side only, so the very first paint
always mismatches the server-rendered shell by design.

**Biome excludes `src/components/ui`** (and `src/styles.css`) from lint/format, same as RCTM_WEB --
vendored shadcn output isn't this project's code style to enforce. If `shadcn add` regenerates a
file with pre-existing lint findings (there are a handful of a11y/hook-dependency nits in the
upstream `sidebar.tsx`/`breadcrumb.tsx`/`field.tsx`/`label.tsx`), that's expected and not something
to hand-fix.

**Components installed**: button, card, table, badge, sonner, dropdown-menu, input, sidebar, field,
skeleton, tooltip, avatar, breadcrumb, label, collapsible, separator, sheet (mirrors RCTM_WEB's set)
plus `table`/`badge` (not in RCTM_WEB, added here because they're what report data actually needs),
and later `select`/`switch` (for the auto-refresh interval/unit picker and its enabled toggle -- see
Architecture). Not everything installed is wired into a page yet (e.g. `sidebar`/`sheet`/
`breadcrumb`/`avatar` -- this app's nav is a simple header, not a full sidebar shell) -- they're
available for when the app grows further. Add more with `bunx shadcn@latest add <name> -y -o`; the
`-o`/`--overwrite` matters once `components.json` is already correct, otherwise re-adding an existing
component no-ops.

## Charts (MUI X Charts)

Both charts on `/atenciones` (`components/status-donut-chart.tsx`, a donut per direction; and
`components/agent-workload-chart.tsx`, a horizontal bar) are built with **MUI X Charts**
(`@mui/x-charts`'s `PieChart`/`BarChart`), replacing an earlier `@tanstack/charts` implementation --
the user explicitly asked to standardize on `mui.com/x/react-charts` for every chart in the app.

- **Peer deps, adopted narrowly**: `@mui/x-charts` has a *mandatory* (non-optional) peer on
  `@mui/material`/`@mui/system`, plus `@emotion/react`/`@emotion/styled` (optional per
  `peerDependenciesMeta`, but `@mui/material` needs them anyway without the zero-runtime/Pigment CSS
  engine, which isn't configured here) -- there's no way to pull in just the charts without them. All
  four are installed, but **only for these two chart components** -- no `MuiThemeProvider`, no other
  MUI component is used anywhere else in the app. The rest of the UI is still shadcn/Base UI/Tailwind;
  don't let MUI creep into other components.
- **Theme colors carry over via CSS custom properties**: both components pass this app's own OKLCH
  theme tokens (`var(--color-chart-2)`, `var(--color-primary)`, etc.) directly as MUI's per-slice
  (`PieValueType.color`) / per-series (`color`) values -- these resolve like any other CSS color at
  paint time, so the guindo/wine palette applies without needing a `MuiThemeProvider` for the *fills*.
- **Chrome (legend/axis/tooltip/grid/arc-stroke) DOES need a theme, unlike the fills above** --
  `components/mui-chart-theme.tsx`'s `ChartThemeProvider` wraps both charts for exactly this. MUI X
  Charts reads legend text (`ChartsLegend.js`), axis tick/line color (`AxisSharedComponents.js`), grid
  lines (`ChartsGrid`), and `PieArc`'s default stroke all from `useTheme().palette.*` -- with no
  `ThemeProvider` that's always MUI's own default *light* theme, regardless of this app's actual dark
  mode. This is exactly what made the initial dark-mode ship "horrible" (near-black legend/axis text
  on a dark card -- unreadable) and gave every donut slice a stray **white border** (`PieArc`'s default
  `stroke` is literally `theme.palette.background.paper`, which defaults to white when unthemed).
  `ChartThemeProvider` fixes both by creating a real MUI theme whose `palette.mode` tracks a
  `MutationObserver` on `<html>`'s `dark` class (the same class `components/theme-provider.tsx` already
  toggles -- reading it directly instead of re-deriving system preference means it can never disagree
  with what's actually painted) and whose `background.paper`/`text.primary`/`text.secondary`/`divider`
  point at this app's own `--color-card`/`--color-foreground`/`--color-muted-foreground`/`--color-border`
  CSS variables -- not a hardcoded light/dark pair, so chart chrome stays pixel-identical to the shadcn
  Card hosting it in both modes with nothing to keep in sync by hand. `status-donut-chart.tsx`
  additionally sets `slotProps={{ pieArc: { stroke: 'none' } }}` -- belt-and-suspenders on top of the
  theme fix, since `paddingAngle` already separates slices and a fully-removed stroke can't ever be the
  wrong color in either mode.
- **Arc label ink is deliberately NOT theme-driven** -- `text.primary` above is a light color in dark
  mode (correct for legend/axis text sitting on the dark card), but arc labels ("82%") sit ON the
  colorful `--chart-2/3/4` fills, which are validated to always need dark ink regardless of app theme
  (see the dataviz skill's "pick ink by the fill's luminance, not the page's" rule). Overridden via
  `sx={{ "& .MuiPieChart-arcLabel": { fill: "#0a0a0a !important", ... } }}` on `<PieChart>` --
  `!important` is deliberate here, fighting the theme's `text.primary` on purpose. (Note the real
  utility class is `MuiPieChart-arcLabel`, not `MuiPieArcLabel-root` -- the latter is only the
  human-readable suffix baked into emotion's per-render hashed class for devtools, e.g.
  `css-1x8dn45-MuiPieArcLabel-root`, and doesn't match as its own CSS selector; an early attempt using
  that wrong selector happened to look fine only because MUI's *unthemed* default `text.primary` is
  already dark, not because the override actually took effect.)
- **Hover-centered value** (`status-donut-chart.tsx`'s `PieCenterLabel`): hovering a slice shows its
  raw count in the donut's center hole. `<PieChart onHighlightChange={...}>` is a real top-level prop
  (confirmed in `PieChart.js`'s own prop list) firing `{ type: 'pie', seriesId, dataIndex } | null` on
  every hover/keyboard-focus change -- no separate highlight-tracking hook needed, just lift
  `dataIndex` into local state and look up `data[dataIndex].value`. The label itself is a plain SVG
  `<text>` passed as `<PieChart>`'s `children` (a real forwarded prop, rendered last inside
  `ChartsSurface`'s `<svg>` -- confirmed in `PieChart.js`), positioned via the `useDrawingArea()` hook's
  `left/top/width/height` (the plotting-area rectangle, excluding the bottom legend's space) rather than
  an absolutely-positioned HTML overlay -- an HTML overlay centered on the whole component's box would
  be offset by the legend's height and land in the wrong spot; SVG coordinates computed from
  `useDrawingArea()` don't have that problem.
- **Tooltips and legend are automatic** -- a real simplification over `@tanstack/charts`, which
  needed explicit `tooltip: { items: [...] }` config (see the fix history below) to avoid showing raw
  coordinates. MUI's default tooltip already shows the right label/value with zero config.
  `slotProps.legend.position.horizontal` is typed `"center" | "start" | "end"` -- not `"middle"`
  (an easy mistake coming from the vertical axis's own `"middle"` value).
- **Horizontal `BarChart` gotcha**: reserving space for long category (agent name) labels on the
  band `yAxis` requires the axis's own `width` property (`yAxis={[{ width: 170, ... }]}`) --
  `margin={{ left: ... }}` alone is silently insufficient (the band axis's default width wins), which
  first showed up as agent names truncated to 2-4 characters ("AN…") even with a large `margin.left`.
  `agent-workload-chart.tsx`'s `AGENT_AXIS_WIDTH_PX` is what actually controls this; the tick label
  itself is separately truncated via `valueFormatter` (`truncateAgentLabel`) so it fits inside that
  reserved width without being clipped mid-character -- the tooltip still shows the full untruncated
  name since it reads the same dataset row, not the formatted tick text.
- **Refresh propagation**: both charts read from `/atenciones`'s route loader
  (`getStatusDistribution`/`getAgentWorkload`), so they refresh through the exact same
  `router.invalidate()` call already used by both the manual "Refresh ahora" button and
  `AutoRefreshProvider`'s timer (see "Client-side auto-refresh" below) -- no chart-specific refresh
  logic exists or is needed. Confirmed live: with `/atenciones` mounted and the auto-refresh interval
  turned down to a few seconds, the timer's `POST /extraction/refresh` was followed immediately by
  fresh `getAgentWorkload`/`getStatusDistribution` calls with no navigation involved.
- **Vite dev-server gotcha (not a code bug)**: adding/removing a dependency in a *currently running*
  `vite dev` process can get its dependency optimizer permanently stuck -- every request for the new
  package 504s with `Outdated Optimize Dep` forever, even across full page reloads, because the
  running process's on-disk `.vite/deps/_metadata.json` never actually gets the new package written
  to it (confirmed by inspecting that file mid-incident: it still listed the just-removed
  `@tanstack/charts` and had no `@mui_x-charts` entry at all, despite the browser requesting a
  specific new hash for it). The fix is a dev server restart (a fresh process re-scans cleanly, logs
  `Re-optimizing dependencies because lockfile has changed`) -- a plain browser refresh is not enough.
  If this happens again after installing a package, don't debug the component code first; restart
  the dev server (or, if it isn't yours to restart, start an independent one on another port to
  verify against, same as this project's established pattern for not touching someone else's running
  process).

## Architecture

**Client-side by default, full-document SSR always** (`src/start.ts`): `createStart(() =>
({ defaultSsr: false }))` makes every route's `beforeLoad`/`loader`/component run client-side unless
a route explicitly opts in (see below). This was a deliberate requirement, not a default left
untouched. The root route's `shellComponent` (`routes/__root.tsx`) is unconditionally SSR'd
regardless of `defaultSsr` -- that's what still gives every response a real server-rendered
`<html>`/`<head>`/`<title>` on the first byte (confirmed live: `curl` shows the title tag present
before any client JS runs), even though the actual route content hydrates client-side. Don't
conflate the two: "full-document SSR" here means the document shell, not the page content.

**Selective SSR per route** -- two routes deliberately override the client-side default in different
directions, to demonstrate (and actually use) both non-`false` modes:

- `routes/reports/$reportName.tsx` sets `ssr: false` explicitly (redundant with the app default, but
  written out so the choice is visible without having to check `start.ts`). Dashboard data with no
  SEO value that can change on every refresh -- nothing here is worth pre-rendering on the server.
- `routes/status.tsx` sets `ssr: 'data-only'`: `beforeLoad`/`loader` run on the server and the
  resolved status is sent to the client for immediate hydration (no loading flicker on first load),
  but the component itself still isn't server-rendered. Confirmed live via Chrome DevTools: the page
  shows the real backend status immediately on load, no fetch spinner.

**Validated search params** (`routes/reports/$reportName.tsx`): `validateSearch:
reportSearchSchema` (zod v4, used directly -- no `@tanstack/zod-adapter` needed since v4 infers
input/output types on its own). `page`/`pageSize` both have `.default(...)`, so `<Link
to="/reports/$reportName" params={...} />` doesn't require passing `search` at all; confirmed live
that navigating without search params redirects to `?page=1&pageSize=50`. Pagination itself is
**server-side**: `loaderDeps` exposes `page`/`pageSize` to the loader, which calls
`getReportRowsPage` (a `createServerFn` proxying to the backend's `GET /data/{report_name}/page`,
see `backend/app/routers/data.py`) instead of fetching every row and slicing client-side -- only the
current page's rows cross the wire on every page change.

**Route loaders + typed server functions** (`routes/reports/$reportName.tsx`,
`server/reports.functions.ts`): the loader validates `params.reportName` against `REPORT_NAMES`
(throwing `notFound()` for an unknown name -- confirmed live) and calls `getReportRowsPage`. A `null`
result (backend's "nothing downloaded yet" signal, see `backend/app/extraction/parsing.py`) is
handled as a distinct UI state, not folded into the 404 case -- it's a normal, expected state for a
fresh deployment, not an error. `getReportRows` (the unpaginated `GET /data/{report_name}` proxy)
still exists and is what `getReportSummary` uses below -- the column-population profile needs every
row regardless of which page is being viewed.

**Streaming**: `getReportSummary` (also a `createServerFn`) computes a column-population profile --
genuinely slower than `getReportRows` because it scans every row (real difference on `contacts`,
~7.5k rows per `ANALYTICS_PLAN.md`). The loader calls it but does **not** await it; returning the
unresolved promise defers it, and the component renders it with `<Await>`, so the table paints
immediately and the summary streams in after. Confirmed live: the "N filas · N columnas" line
appears fractionally after the table itself. (TanStack Start also supports `ReadableStream`/async-
generator streaming directly from a server function -- see the "Streaming Data from Server
Functions" guide -- but nothing here needed chunk-by-chunk streaming, so that pattern isn't used;
don't add it speculatively.)

**Typed server function mutation** (`routes/status.tsx`, `components/auto-refresh-provider.tsx`):
`triggerRefresh` is a `POST` `createServerFn` proxying to the backend's `POST /extraction/refresh`.
Called two ways: manually via `useServerFn(triggerRefresh)` in `status.tsx`'s "Refresh ahora" button
(the documented way to call a server function from an event handler), and automatically on a timer
by `AutoRefreshProvider` (see below). Both follow up with `router.invalidate()` to reflect the new
status/data. **This is a real, consequential action** -- it makes the backend log into the live
`casamarket.c3.pe` and run a real download cycle. Don't trigger it (manually, or by turning
auto-refresh on with a short interval) just to test the UI; the read-only routes (`/reports/*`) are
enough to verify the frontend/backend wiring.

**`/atenciones`'s per-day filter reads history, not the latest snapshot** (`routes/atenciones.tsx`,
`lib/date-filter.ts`): the `date` search param (`'YYYY-MM-DD' | 'all'`) is a `loaderDeps`, so changing
it re-runs the loader, which calls `getAttentionsAnalytics`/`getIncidentAnalytics` with that date.
Those two `createServerFn`s fetch from the backend's `GET /data/{report_name}/history` (every
downloaded day's file for that report, concatenated -- see `backend/CLAUDE.md`'s
`parse_report_history` note), then `filterRowsByDate` (`lib/date-filter.ts`) keeps only the rows whose
own date column (`"Fecha registro"` for attentions, `"Fecha"` for calls -- differs per report, see
`INCIDENT_DATE_FIELD` in `lib/incident-analytics.ts`) matches the selected day. `'all'` is a no-op
(no filtering). This is why picking a past day can show real data at all: the regular refresh (and
the backend's C3 export request) only ever covers "today" -- the day-range comes from *which
already-downloaded files* get read, not from asking C3 for a wider window.

**Defaults to today, not `'all'`** (`server/schemas.ts`'s `attentionsSearchSchema`): a fresh visit to
`/atenciones` should show today's atenciones, not every historical day merged together -- `'all'` is
still reachable via the clear ("Quitar filtro de fecha") button, just not the landing state.
`dateFilterValue.default(todayIsoDate)` -- a zod default can be a thunk, called on every parse -- and
`todayIsoDate()` computes "today" from `Intl.DateTimeFormat` pinned to `America/Lima`, **not** the
executing machine's local clock: this can run server-side during SSR, where "local" would be whatever
timezone the Node process happens to be in, not the browser's. Mirrors why the backend's `config.hoy()`
does the same pinning (`backend/app/config.py`) -- both exist so a naive local-clock "today" can't
drift by a day near midnight relative to the other.

**The "Refresh ahora" button on `/atenciones` is context-aware, tied to that same `date` filter**:
`handleRefresh` checks `isPastDaySelected` (`date !== 'all' && date !== todayIsoDate()`) -- false (the
default-today or explicit-all case) calls the regular `triggerRefresh` (today only, same as
`/status`'s button); true (an actual past day picked) calls `triggerBackfill({ data: { date } })`
instead, i.e. re-fetches *that* day from C3 rather than today. `'all'` and "today" are treated the same
here on purpose: a backfill *of* today would do the same C3 request as a regular refresh anyway, so
there's no reason to route through the backfill call, or to have the button read `` `Backfill
${today}` `` on a plain page load. This was a deliberate fix, not the original design -- clicking
refresh with a past day selected used to silently still only refresh today, doing nothing useful for
the selected day (`triggerRefresh` has no concept of "which day", see the note below). The button's
label reflects which action will actually run (`"Refresh ahora"` vs `` `Backfill ${date}` ``) so this
isn't a hidden behavior switch.

**Backfilling one past day is a separate, manual-only mutation** --
`triggerBackfill`/`getBackfillStatus` (`server/reports.functions.ts`) proxy to the
backend's dedicated `POST /extraction/backfill` / `GET /extraction/backfill/status`
(`backend/CLAUDE.md`'s "Backfilling a past day" note has the full why, including that contacts is
deliberately excluded -- its export has no date range at all). Surfaced two ways: `status.tsx`'s
`BackfillCard` (a date input + its own "Backfill" button, independent of any other page's state) and,
as of the note above, `/atenciones`'s "Refresh ahora" button when a specific day is selected there.
Both eventually call the same server function -- there's no separate "atenciones backfill" codepath,
just a different caller choosing when to invoke it.

**Client-side auto-refresh** (`components/auto-refresh-provider.tsx`,
`lib/auto-refresh-settings.ts`) -- **this is what replaced the backend's scheduler**. The backend
used to run an internal APScheduler daily cron (see `backend/CLAUDE.md`'s "no scheduler here" note);
that was removed, and this provider is the replacement: mounted once in `routes/__root.tsx` (wrapping
everything, inside `ThemeProvider`), it keeps calling `POST /extraction/refresh` on a configurable
interval for as long as the app is open in a tab.

- **Read this tradeoff before touching it**: a client-side timer only runs while a browser tab has
  the app open. Close every tab and extraction stops entirely -- there is no server-side fallback.
  This was an explicit, deliberate choice (the user asked to move the cron client-side and remove the
  server one), not an oversight; if that's ever wrong for this deployment, the fix is bringing a
  scheduler back on the backend, not patching around it here.
- **Settings** (`lib/auto-refresh-settings.ts`): `{ enabled, value, unit }`, `unit` one of
  `"seconds" | "minutes" | "hours"`, default `{ enabled: true, value: 5, unit: "minutes" }`.
  Persisted to `localStorage` (key `c3-panel:auto-refresh-settings`) so the interval survives a
  reload -- it does **not** survive closing the tab in the sense of "keep counting down"; the timer
  restarts fresh from zero on the next load, it just remembers *what interval* to use.
  `loadAutoRefreshSettings()` validates the shape and falls back to the default on anything
  malformed (corrupted storage, an old shape from a future settings-schema change, SSR with no
  `localStorage`), so a bad stored value can never crash the app.
- **Scheduling mechanism**: recursive `setTimeout`, not `setInterval` -- `AutoRefreshProvider`
  schedules the *next* tick only after the current one settles (success or error), so a slow request
  or a backend hiccup can't pile up overlapping calls. The effect re-runs (clearing and rescheduling)
  whenever `settings` changes, so saving a new interval on `/status` takes effect immediately instead
  of waiting out the old schedule.
- **Error handling**: a `409` (the backend's `AlreadyRunningError` -- another refresh, manual or from
  a second tab's own timer, already in flight) is swallowed silently; it's an expected race under a
  short interval or multiple tabs open, not a real failure. Any other error sets `lastError` (shown on
  `/status`) and raises a `sonner` toast -- auto-refresh failures are surfaced, not silent, since
  there's no server log a user would otherwise see them in.
- **Settings UI** (`routes/status.tsx`'s `AutoRefreshSettingsCard`): a `Switch` (enabled), an `Input`
  (value) + `Select` (unit), and an explicit "Guardar" button -- deliberately **not** auto-saving on
  every keystroke/change, which would reschedule the timer on every character typed into the number
  field. Local "draft" state holds the in-progress edit; only `Guardar` calls `setSettings()` (which
  persists and reschedules). One `shadcn` gotcha hit here: Base UI's `<Select.Value>` shows the raw
  `value` unless given a formatter function as `children` -- unlike Radix, it does not automatically
  mirror the matching `<SelectItem>`'s rendered label.

**Deployment target** (`vite.config.ts`): `nitro({ preset: 'bun' })`. Nitro is the "deploy
anywhere" adapter Start's own docs recommend when you don't want to commit to one hosting vendor's
plugin (Cloudflare/Netlify/Vercel each have their own); `preset: 'bun'` targets this project's
already-standard runtime (bun is the package manager and dev server here) without touching any
application code -- retargeting to a different host is a one-line preset change, not a rewrite. Build
output: `.output/public` (client assets) + `.output/server/index.mjs` (the server entry `bun run
start` runs).
